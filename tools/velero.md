# Velero

Velero is an open-source tool that backs up and restores Kubernetes cluster resources and persistent volume data to object storage, so you can recover from a deleted namespace, a broken upgrade or a lost cluster, or move workloads between clusters.

## Why teams adopt it

"Everything is in Git" covers less of a cluster than people expect. GitOps restores the manifests you committed. It doesn't restore the data in PersistentVolumes, Secrets created out of band, resources generated by operators, CRD instances that users created through an API, or the state of the cluster at 02:00 last Tuesday. An etcd snapshot covers the API state, but it's all-or-nothing, it's tied to that one control plane, and on managed Kubernetes (EKS, GKE, AKS) you can't take one at all.

Velero works at the Kubernetes API level instead. It runs as a Deployment in the cluster, queries the API server for the resources you select, writes them as a tarball of JSON to an object storage bucket, and captures volume data alongside. Because a backup is just API objects plus volume data, you can restore it selectively (one namespace, one label selector, one resource type) and into a different cluster.

The core concepts:
- **Backup**: a point-in-time capture of selected resources and volumes. Filter by namespace, label selector or resource type.
- **Schedule**: a cron expression that creates Backups, each with a TTL after which it's garbage collected.
- **Restore**: replays a Backup into a cluster, optionally remapping namespaces.
- **BackupStorageLocation (BSL)**: the bucket where backup metadata and file-level volume data live. S3, GCS, Azure Blob and anything S3-compatible (MinIO, Ceph) work through provider plugins.
- **VolumeSnapshotLocation (VSL)**: where native disk snapshots are taken, for providers that support them.

Volume data can be captured three ways, and choosing between them is the main design decision:
- **Native or CSI snapshots**: Velero asks the cloud provider or CSI driver for a disk snapshot. This is fast and incremental, but the snapshot usually stays in the same cloud account and region as the disk.
- **File system backup (FSB)**: a node-agent DaemonSet reads the volume's files from the node and uploads them to the bucket with Kopia. It works with almost any volume type and the data is portable, but it's slower and reads a live file system.
- **CSI snapshot data movement**: Velero takes a CSI snapshot, then the node agent copies its contents to the bucket. You get a consistent snapshot as the source and a portable copy in object storage, at the cost of more moving parts.

Common adoption triggers:
- Someone ran `kubectl delete ns` against the wrong context, and recovery took a day.
- Compliance or a customer contract requires documented, tested backup and restore with a stated RPO and RTO.
- You're migrating between clusters, cloud providers or regions and want to move stateful workloads without rebuilding them by hand.
- You're about to do a risky in-place change (a Kubernetes minor upgrade, a CRD version migration, an operator upgrade) and want a way back.
- You run on managed Kubernetes and have no access to etcd.

## Basic usage

**1. Install the server into a cluster, pointed at an S3 bucket:**
```bash
# credentials-velero is an AWS-style credentials file with access to the bucket.
# Pick the plugin tag that matches your Velero version (see the plugin's compatibility table).
velero install \
  --provider aws \
  --plugins velero/velero-plugin-for-aws:<version> \
  --bucket my-cluster-backups \
  --backup-location-config region=us-east-1 \
  --snapshot-location-config region=us-east-1 \
  --secret-file ./credentials-velero \
  --use-node-agent            # deploys the DaemonSet needed for file system backup

# Check that the bucket is reachable. The BSL should show "Available".
velero backup-location get
```

**2. Take a one-off backup, then schedule a recurring one:**
```bash
# Back up one namespace, including its volumes.
velero backup create shop-pre-upgrade --include-namespaces shop --wait

# Inspect what was captured, and any warnings or errors.
velero backup describe shop-pre-upgrade --details
velero backup logs shop-pre-upgrade

# Back up everything labelled tier=critical every night at 02:00 UTC, keep for 30 days.
velero schedule create nightly-critical \
  --schedule "0 2 * * *" \
  --selector tier=critical \
  --ttl 720h
```

**3. Restore, in place or into a different namespace:**
```bash
# Restore the whole backup.
velero restore create --from-backup shop-pre-upgrade --wait

# Restore only ConfigMaps and Secrets from it.
velero restore create --from-backup shop-pre-upgrade \
  --include-resources configmaps,secrets

# Restore into a scratch namespace to inspect data without touching the live one.
velero restore create shop-verify \
  --from-backup shop-pre-upgrade \
  --namespace-mappings shop:shop-verify

velero restore describe shop-verify --details
```

**Bonus: quiesce a database before its volume is captured.** Hooks are pod annotations that run a command in a container before and after the backup of that pod:
```yaml
metadata:
  annotations:
    pre.hook.backup.velero.io/container: postgres
    pre.hook.backup.velero.io/command: '["/bin/sh", "-c", "psql -U postgres -c CHECKPOINT"]'
    post.hook.backup.velero.io/command: '["/bin/sh", "-c", "echo backup done"]'
    # Opt this pod's "data" volume into file system backup.
    backup.velero.io/backup-volumes: data
```

## Common pitfalls

- **An untested backup isn't a backup.** A Backup can report `Completed` and still be missing the volume data you care about. Read `velero backup describe --details` for the per-volume results, and run a scheduled restore into a scratch namespace or cluster. `PartiallyFailed` is a status people learn to ignore, and they shouldn't.
- **Volume data isn't captured unless you set it up.** Without a snapshot-capable provider or CSI configuration, and without opting volumes into file system backup, Velero saves the PVC and PV objects and none of the bytes. Either annotate pods, or set `--default-volumes-to-fs-backup` and opt out the volumes you don't want.
- **Restores don't overwrite by default.** If a resource already exists in the target cluster, Velero skips it and logs a warning. This surprises people who expect "restore" to mean "roll back to". Either delete the namespace first, restore into a new one, or use `--existing-resource-policy=update`, which patches existing objects but still won't replace volume contents.
- **Snapshots can share a blast radius with the thing they protect.** Native disk snapshots usually live in the same account and region as the cluster. If the account is compromised or the region is down, they go too. Use file system backup or snapshot data movement to get data into a bucket, and put that bucket in another account or region with versioning or object lock.
- **Backups are crash-consistent unless you make them application-consistent.** Snapshots and file copies of a running database capture whatever was on disk. Most databases recover from that, but for anything important use hooks to flush or freeze, or back up with the database's own tooling (`pg_dump`, WAL archiving, an operator's backup CRD) and let Velero cover the Kubernetes objects.
- **File system backup has limits.** It doesn't support `hostPath` volumes, it reads files while they're changing, and its speed depends on file count as much as bytes. Millions of small files are slow. Give the node agent real CPU and memory requests, because the defaults are tuned for small volumes.
- **Order and dependencies on restore.** Velero restores in a fixed resource order (CRDs, namespaces, storage classes, PVs, PVCs, and so on before workloads), but operators add their own ordering needs. A custom resource restored before its operator is running may sit unreconciled, and one restored with a stale `status` or owner reference can confuse the operator. Restore the operator first, then its custom resources, for anything stateful.
- **Cross-cluster restores hit environment differences.** Storage class names, availability zones on PV node affinity, load balancer annotations, ingress classes and API versions removed in the newer Kubernetes release all differ between clusters. Velero can remap storage classes with a ConfigMap and convert some API versions, but plan for a dry run.
- **Two clusters writing to one backup location will fight.** When a second cluster points at the same bucket and prefix, for example a DR cluster, set its BSL to `--access-mode ReadOnly` so it can restore but can't delete or expire the primary's backups.
- **It isn't a control plane backup.** Velero recreates objects through the API server. It doesn't restore etcd, node state, cluster certificates or anything outside Kubernetes such as IAM roles, DNS records and the load balancers themselves. You still need infrastructure as code to rebuild the cluster that Velero restores into.
- **TTL deletes quietly.** The default TTL is 30 days. If your retention requirement is longer, set `--ttl` explicitly on every Schedule, and alert on the `velero_backup_last_successful_timestamp` metric so a schedule that stopped succeeding weeks ago doesn't go unnoticed until you need it.
