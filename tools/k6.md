# k6

k6 is an open-source, developer-centric load testing tool (built by Grafana Labs) that lets engineers write performance tests as code in JavaScript and run them from the command line or CI, so that a service's behavior under real traffic can be verified before it's discovered in production.

## Primary use cases

- **Pre-launch capacity checks**: before a new endpoint, service, or feature ships, simulate realistic concurrent traffic to find its breaking point (max RPS, latency under load, error rate) rather than guessing.
- **Regression testing for performance**: run the same load test on every PR or nightly build in CI, and fail the pipeline if p95 latency or error rate crosses a threshold — performance budgets enforced the same way unit tests enforce correctness.
- **Capacity planning for platform teams**: model expected peak traffic (e.g., Black Friday, a marketing campaign, a migration cutover) against staging or a canary to validate autoscaling policies and resource limits before the real event.
- **API and microservice reliability testing**: chain multiple requests (auth, then a sequence of calls) to test realistic user flows, not just single endpoints, and catch issues that only appear under concurrent load (connection pool exhaustion, lock contention, cache stampedes).
- **SLO validation**: teams that define SLOs (e.g., "p99 < 300ms at 500 RPS") use k6's built-in thresholds to make that measurable and automatically pass/fail.

A team typically adopts k6 once they've been burned by a launch that fell over under real traffic, or when they want performance testing to live in version control alongside the code instead of being a manual, pre-launch fire drill run by one person with a proprietary tool.

## Basic usage

**1. Install and run an inline script**

```bash
brew install k6   # or: apt install k6, docker run grafana/k6

cat <<'EOF' > script.js
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  vus: 20,          // 20 virtual users
  duration: '30s',
};

export default function () {
  const res = http.get('https://test-api.example.com/status');
  check(res, { 'status is 200': (r) => r.status === 200 });
  sleep(1);
}
EOF

k6 run script.js
```

**2. Ramp traffic up and down with stages**

```javascript
export const options = {
  stages: [
    { duration: '1m', target: 50 },   // ramp up to 50 VUs
    { duration: '3m', target: 50 },   // hold steady
    { duration: '1m', target: 0 },    // ramp down
  ],
  thresholds: {
    http_req_duration: ['p(95)<500'],  // fail if p95 > 500ms
    http_req_failed: ['rate<0.01'],    // fail if error rate > 1%
  },
};
```

**3. Test a multi-step flow (login, then authenticated request)**

```javascript
import http from 'k6/http';
import { check } from 'k6';

export default function () {
  const loginRes = http.post('https://test-api.example.com/login', {
    username: 'test', password: 'test',
  });
  const token = loginRes.json('token');

  const res = http.get('https://test-api.example.com/profile', {
    headers: { Authorization: `Bearer ${token}` },
  });
  check(res, { 'profile loaded': (r) => r.status === 200 });
}
```

Run with `k6 run --out json=results.json script.js` to export results, or `--out experimental-prometheus-rw` to stream metrics straight into Grafana for live dashboards during the run.

## Common pitfalls

- **Testing against production by accident** — k6 will happily generate real load. Always confirm the target environment and get sign-off before pointing a ramp-up test at anything shared, and never run un-throttled tests against third-party APIs you don't own.
- **VUs are not requests-per-second** — a "virtual user" loops through the script as fast as it can (or per your `sleep` calls), so 100 VUs doesn't mean 100 RPS; use the `constant-arrival-rate` or `ramping-arrival-rate` executors when you need to control throughput precisely rather than concurrency.
- **Client-side bottlenecks skew results** — running a high-VU test from a single underpowered machine or laptop can make k6 itself the bottleneck. For serious load, run distributed (k6 Cloud, or multiple k6 instances behind a coordinator) and watch k6's own CPU/network usage.
- **Cold caches and warm-up effects** — the first minute of a test often shows inflated latency as caches, connection pools, and JIT/autoscaling catch up. Exclude warm-up periods from threshold evaluation or use `stages` to ramp gradually instead of slamming full load at t=0.
- **Not modeling realistic think-time or payloads** — a tight loop with no `sleep()` and hardcoded identical payloads tests an unrealistic scenario (and can trivially trigger caching or rate limiting) that doesn't reflect real user behavior. Parameterize inputs and add representative pacing.
- **Ignoring downstream blast radius** — a load test against a service that shares a database, queue, or third-party dependency with other production traffic can degrade other systems. Coordinate load tests the same way you'd coordinate a deploy.
